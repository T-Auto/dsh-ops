# `symbol_map` —— 花多少、省多少

环境 Windows 11 / x64、Node 24.22.1，三轮取中位；对象是生成的 400 行 TypeScript 文件（8 KiB），
已安装 tree-sitter 语法包。

| 路径 | 耗时 | 渲染字节 | 估算 token |
| --- | --- | --- | --- |
| `symbol_map`（热态） | **0.13 ms** | 1 282 | **321** |
| 同一文件的整篇读 | 0.84 ms | 5 039 | 1 260 |

相对 schema 默认读（200 行）：**省 74.6 % token、快 83.7 %**。相对整篇读则省 88 %；但 200 行默认本身
已经截断，所以 74.6 % 才是调用方真正会付出的差额。

## 冷启动

对某个文件的第一次调用要付解析成本：**14.7 ms**；之后命中进程内的符号表缓存，降到 0.13 ms。一个会话里
每个文件只冷一次。

## 为什么答案这么小

回执每个符号一行位置（`start-end kind name`），加文件身份（`revision`、`fileHash`），永远没有符号正文。
这不只是体积决定：大纲不能替代读取，所以 `symbol_map` 不在 `OBSERVED_READ_TOOLS` 里，只看大纲就去编辑
仍然过不了 compare-and-swap。

## 降级行为

| 缺失 | 行为 |
| --- | --- |
| tree-sitter 语法包 | 以 `EXECUTOR_UNAVAILABLE` 给出确切安装命令，绝不返回空大纲 |
| worker 二进制 | 无影响——本工具从不启动它 |

`test/symbol-map.test.mjs` 把上述行为全部钉成断言（47 项），包括“语法错误文件仍给出错误行以下的符号”
与“恢复出的区间绝不是凭空造的”。
