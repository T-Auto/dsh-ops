# 原生原始输出溢写基础

English: [Native raw output spill foundation](native-raw-spill.md)

此 #872 内部切片为 Windows 进程范围添加可恢复的原始输出。仓库示例通过公共
subprocess 与 sandbox provider 实际运行；不发布任务工具，不替换现有 Shell runner，
也不宣称持久会话已具备完整输出能力。POSIX 范围仍明确不受支持，既有 POSIX 执行保持不变。

## 存储与观测

每个原生所有者配置一个 `SpillStore`，各范围共享其克隆。构造只检查绝对根路径与字节上限，
不在协调线程执行文件系统操作。首次超出内存预算时，由该流现有的输出读取线程创建共享
私有目录。目录创建失败会缓存，并以 `spillError` 降级保留有界内存尾部，不使内核启动或
文件工具失败。

任务示例每条流保留 64,000 个原始字节。溢出后延迟创建的文件从字节零保存完整流，最大
64 MiB。每次有界写入完成后，才一起提交对应的已观察计数、尾部和路径。快照/读取锁从不
覆盖文件系统 I/O；写入等待期间仍可读取上一份快照。已公布的实时路径覆盖该快照全部
已报告字节，但 `spillSealed` 此时仍为 false。

可选协议字段为 `spillPath`、`spillOrigin: "ops-native-v1"`、`spillPid`、
`spillSealed` 和独立的 `spillError`。适配器必须将 `spillPid` 与实际常驻内核 PID
核对，而非 Node 宿主 PID。原始读取失败时 EOF 保持 false；仅溢写降级不会伪造原始读取
失败。超过上限、写入失败或封存失败会撤回并丢弃完整文件，继续排空并保留有界尾部。

文件使用 owner/SYSTEM ACL、不可预测名称、独占创建，并对每层祖先及打开的目录/文件
执行不跟随检查。持有的目录句柄禁止目录重命名。未封存文件采用 delete-on-close；仅在
原始 EOF 后，经检查的封存操作才清除此状态。因此已验证路径中内核突然死亡会删除未完成
文件，已封存文件则继续可恢复。

## 取消与失败边界

现有输出读取线程持有文件、操作、缓冲区及完成事件，每次最多写入 8 KiB。取消操作针对
确切的写线程与文件；待完成 OVERLAPPED 的缓冲区一直保留到观察到操作完成。加入失败或
超时不会分离读取线程。

Windows 取消请求不证明文件系统驱动已经停止。如果 `captures_until(deadline)` 无法
加入线程，或经检查的丢弃操作无法完成，`cleanup_unconfirmed()` 将为 true。
[Windows 取消契约](https://learn.microsoft.com/en-us/windows/win32/fileio/canceling-pending-i-o-operations)
要求在释放操作资源前观察到操作完成。
必须关闭
该原生所有者的准入，保留 Range/读取线程，并独立关闭控制管道，由公共宿主终止并加入
整个受管理内核范围。不得将该任务报告为独立清理完成，不得复用 Range，也不得在已中毒
所有者下创建新范围。`Drop` 会保留未加入的线程，不能代替这一致命传输回调。关闭或删除
状态设置失败意味着清理不确定，不能声称所有文件均已删除。
中毒状态不可逆：迟到字节可以更新有界诊断尾部，但不能清除原始错误、恢复 EOF 或重新
公布完整路径。读取线程观察到中毒后会丢弃文件而非封存。已经在途的封存仍可能稍后完成；
该路径保持撤回，所有者仍须由宿主整体终止，不能据此声称文件清理成功。

## 恢复与保留

现有溢写账本新增可选原生来源。原生路径必须符合
`<真实 temp>/dsh-ops-native-<内核 PID>-<32 位 hex>/`
`{stdout,stderr}-<32 位 hex>.log`，记录 PID 必须匹配目录，完整字节数不超过 64 MiB。
旧宿主 provider 记录不变。仅在线程加入且文件封存后才写入结算账本。保留扫描拒绝符号
链接/junction 祖先及非普通文件，保留既有所有权检查，并通过同一个有界清理过程逐个
删除文件，不新增第二套账本或后台清理服务。

已结算文件使用既有绝对路径文件读取权限。凭据边界及原生不跟随检查仍然生效，
workspace-write 权限不会获得修改这些文件的能力。实际探针通过 `inspect_local_file`
读取溢写头部，并验证相应写入被拒绝；没有添加任意临时目录写权限。

## 验证与后续工作

Windows CI 运行 `probe-872-spill.mjs` 和 `probe-872-spill-fatal.mjs`。前者验证精确
内存边界、实时/封存恢复、精确 64 MiB 上限、取消流封存、共享保留和内核硬退出清理。
后者显式调用仅供测试的不响应写入，观察清理不确定及所有者仍被保留，再加入公共宿主
终止，并证明宿主可以运行另一个独立拥有的进程。原生测试还验证真实待完成 I/O 取消、
延迟目录失败、重解析拒绝、写入/封存失败。测试发现阶段标为 ignored 的原生子进程夹具
由这些测试或探针显式执行，并非功能跳过。

[任务集成](常驻任务输出与保留.md)现已在就绪前配置同一个存储，传递完整原生元数据，
并将已封存文件登记到既有账本。持久私有通道仍使用既有前缀保留；其存储与会话适配器
集成仍待完成。仅 `task-v1` 不代表溢写能力对等；生产启用还必须要求已完成的
`task-spill-v1` 能力。
