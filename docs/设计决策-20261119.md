## 一个输入如何到达工具集合

| 阶段 | 位置 | 作用 |
| --- | --- | --- |
| 行/全局键 | `src/settings/merged.ts` `resolveMergedConfig` | 校验行配置；`dynamicTools` 与 `residentTools` 默认 true（`global` 没有常驻键） |
| 与门 | `effectiveMode`（`src/settings/merged.ts`）、`dynamicForMode` | 行 `dynamicTools` 与 `global.dynamicTools` 求与；总开关「保留操作者意图，只是不再生效」 |
| 消费者计划 | `src/presets/builtin.ts` `applyResolvedMode` | `gate.resident = config.residentTools`，`gate.dynamic = config.dynamicTools`（过门后的值），`plan.ptc = { allowedTools, alwaysLoaded }` |
| 发布 | `src/publication/ptc.ts` `mountPtc` | `resident` = `PTC_RESIDENT_TOOLS` + `alwaysLoaded`，`gate.resident === false` 时为空；`selectable` = `allowedTools` + `result`，`gate.dynamic === false` 时为空；工具在常驻**或**已被选中时可调；`ops_load_sdk` 仅在 `gate.dynamic !== false` 时发布 |

## 真值表

以 `ops-ptc` 行为准（`ptc` 行首轮集合相同，仅 `batchingGuidance` 缺省不同）。测量环境：
Linux、`danger-full-access`、native worker 就位、真实 PTC 呈现、宿主官方
`read`/`glob`/`grep` 保持可见；`ops_bash` 缺席，因为 POSIX 行沿用宿主 shell。

| # | 输入（`dsh-ops` 行配置的一行） | 本步可调 | 可加载未加载 | loader | run_code 首轮视角 |
| --- | --- | --- | --- | --- | --- |
| 1 | 缺省（无任何键） | `ops_inspect_local_file`、`ops_load_sdk` | 下方十六个 API 的默认池 | 有 | `tools.ops_inspect_local_file` 与 `tools.ops_load_sdk` 可用；`ops_load_sdk({tools:['grep']})` 回执 completed，但 `ops_grep` 要到**下一个**程序才可调 |
| 2 | `global: {dynamicTools: false}` | `ops_inspect_local_file` | 无 | 无 | `tools.ops_inspect_local_file` 可用；没有 `tools.ops_load_sdk` |
| 3 | `ops-ptc: {dynamicTools: false}` | `ops_inspect_local_file` | 无 | 无 | 与第 2 行同一集合（同一个与门的两侧），差别只在作用域——见注 |
| 4 | 第 3 行再加 `ops-ptc: {alwaysLoaded: [stat]}` | `ops_inspect_local_file`、`ops_stat` | 无 | 无 | 两个绑定首轮即可调用 |
| 5 | `ops-ptc: {residentTools: false}` | `ops_load_sdk` | 下方十六个 API 的默认池 | 有 | loader 是唯一绑定；`ops_inspect_local_file` 整体不可达——`ops_load_sdk({tools:['inspect_local_file']})` 回 `INVALID_ARGUMENT` |
| T | **已实现——见 D3 附录**：显式选择全量且 `allowedTools: [grep, stat]` | `ops_grep`、`ops_stat`（依 #979 §2） | — | 无（依 #979 §2） | 获准 API 首轮全部可调；只读会话仍排除写 API |

默认可加载池（第 1、5 行）恰为：
`ops_grep`、`ops_glob`、`ops_replace`、`ops_write_file`、`ops_edit_file`、`ops_diff`、
`ops_stat`、`ops_copy`、`ops_move`、`ops_remove`、`ops_read_files`、`ops_read_table`、
`ops_read_docx`、`ops_read_pdf`、`ops_batch`、`ops_result`——十六个非常驻原始 API
（`PTC_LOADABLE_TOOLS`）。目标行 T 的池为 `ops_grep`、`ops_stat` **外加
`ops_result`**（见签字决定项 1）。

**逐行注释。**

- 第 2、3 行发布同一个 OPS 集合，因为它们喂进同一个与门。但输入本身不同：总开关
  同时关掉 `standard`/`cordis`/`minimal` 的 Native 发现入口（`dynamicForMode`），
  行级开关只影响本行。
- 第 4 行说明 `dynamicTools:false` **不**压制 `alwaysLoaded`：启动名单随常驻集合发布，
  只是没有 loader 去选择上限中的其余工具。
- 第 5 行说明 `residentTools:false` 丢掉整个常驻集合，包括 `ops_inspect_local_file`，
  而且它也加载不回来（不在 `PTC_LOADABLE_TOOLS` 里）。
- **旧行关闭与全量选择是两个不同的输入**（#985 反例）：`allowedTools: [grep, stat]` 加
  `dynamicTools: false` 时，首轮只有 `ops_inspect_local_file`——没有 `ops_grep`、没有
  `ops_stat`、没有 loader。把 `dynamicTools:false` 解读成「发布全部获准工具」，就会让
  `ops_grep`、`ops_stat` 出现在这一轮，改变旧用户的成本与权限预期；#907 曾隐式做过
  这个翻转，#910 随即撤回（#979 §4）。

**只读与可写实例。** 默认池中的只读成员：`ops_grep`、`ops_stat`、`ops_glob`、
`ops_diff`、`ops_read_files`、`ops_read_table`、`ops_read_docx`、`ops_read_pdf`。
可写成员：`ops_replace`、`ops_write_file`、`ops_edit_file`、`ops_copy`、`ops_move`、
`ops_remove`、`ops_batch`。只读会话下，`permitted`（`src/publication/ptc.ts`）会把所有
会变更的 API 从可加载池中剔除，加载请求回 `INVALID_ARGUMENT`；`ops_result` 与
`ops_load_sdk` 豁免于该变更检查。本卡没有测试切换沙箱模式；只读由 D3 覆盖。

一段可以逐字照抄的程序：

```js
// plan: 第 1 行——现在加载 grep，下一个程序再使用
const picked = await tools.ops_load_sdk({ tools: ['grep'] })
return { picked } // picked.status === 'completed'；ops_grep 在本程序内仍不可调
```

```js
// plan: 第 4 行——stat 在此行常驻，首轮即可调用
const r = await tools.ops_stat({ path: 'a' })
return r.status
```

## 维护者签字决定项——如实记录，刻意不实现

1. **`ops_result` 的隐式例外。** 今天 `loadable = [...allowedTools, 'result']` 无条件成立，
   且 `permitted` 让 `result` 豁免只读变更检查，因此即使上限没写它，`ops_result` 也始终
   可加载（现状由 `test/resident-switch.test.mjs` 的 "result exception remains loadable"
   覆盖）。而 `dynamicTools:false`（第 2–4 行）下 `ops_result` **根本不发布**。全量档需要
   决定：首轮是否发布 `ops_result`，让落盘的 ref 仍然可消费（#979 §3）？当前行为已锁定，
   本文不做任何改动。（已由 D3 附录解决：全量档首轮发布 `ops_result`。）
2. **总开关对显式全量选择的作用。** 今天 `global.dynamicTools` 与门控住每一行的 loader，
   PTC 行也不例外。#979 §4 要求升级、保存设置和 `global.dynamicTools` 开关都不得替用户
   选择全量。需要决定：`global.dynamicTools:false` 是否也压制显式选择全量的行，还是显式
   opt-in 优先于总开关？
3. **显式常驻与上限的冲突。** 今天 `alwaysLoaded` 只对照可加载池校验
   （`src/ptc/config.ts`），从不对照 `allowedTools`：`{ allowedTools: [grep],
   alwaysLoaded: [stat] }` 会把 `stat` 当常驻发布且没有任何诊断；`residentTools:false`
   则静默丢弃整个常驻集合（含 `alwaysLoaded`）。需要决定：D2 给哪些冲突加可读诊断、
   `alwaysLoaded` 是否必须落在 `allowedTools` 之内。
   补录对比事实（同日追加，只记录不实现）：**自定义 integration 路径**更严——
   `src/consumer/options.ts:100` 对 `alwaysLoaded` 不在 `allowedTools` 内的自定义 PTC
   配置直接抛 `alwaysLoaded must be in allowedTools`，而内置行对同一形状静默接受
   （已由套件「escapes the allowedTools cap」检查锁定）。该诊断不一致已由 D4 卡
   （#988）认领修复；D1 只记录现状。
4. **合法自定义 PTC integration 被误诊 `ops_result` 未发布。**
   `src/integration/diagnostics.ts` 把 `'result'` 列入每个 PTC integration 作用域的
   首轮期望可见名，但 `result` 是可选加载而非常驻（`PTC_RESIDENT_TOOLS` 仅
   `inspect_local_file` 一个），只有 loader 选中后才可见。于是完全合法的自定义
   `profile: 'ptc'` integration 会被诊断为 `degraded`，报
   `PUBLICATION_UNAVAILABLE: ops_result`，而它唯一的「缺口」是一个尚未被加载的
   API——已实测启动这样一个 integration 证实，并由套件的
   「misdiagnosed PUBLICATION_UNAVAILABLE」检查锁定。内置模式行根本不挂诊断
   （`mountDiagnostics` 只在 `mountIntegration` 中运行），因此该误报只可能出现在
   自定义 integration 路径上。修复已由 D4 卡（#988）认领；D1 只记录现状。

## 设置页文案——如实照录

设置页与行开关把 dynamic-tools 开关描述为「发现入口」。已发布文案照录自
`src/client/locales.ts`：

| 键 | 英文 | 中文 |
| --- | --- | --- |
| `dynamicToolsHint` | "When off, no preset offers the discovery entry." | "关闭后没有任何预设提供发现入口。" |
| `swDynamicToolsHint` | "Offers the discovery entry to this preset. Applies only while the bundle switch is on." | "为该预设提供发现入口。仅在总开关开启时生效。" |

PTC 行实际为该入口发布的是类型化 loader `ops_load_sdk`（真值表第 1、5 行），
并非发现式工具：措辞与产物存在差异。统一措辞属 #979 的 D5 切片；本卡只记录差异。

## Loader 分批——如实记录现状

一次 `ops_load_sdk` 调用接受 1–5 个精确原始 API 名
（`src/projections/ptc/loader.ts` 的 `requestedApis`——
`tools must contain 1-5 exact raw API names`），因此装满十六名默认池至少需要四次
调用。`alwaysLoaded` 与其余常驻集合没有数量上限：`parsePtcConfig`
（`src/ptc/config.ts`）只逐名对照可加载池校验，从不校验名单长度，且常驻 API
无需任何 loader 调用即发布。由套件「loader batches 1-5 names」检查锁定。

## D2 附录——显式披露策略键已解析（2026-11-19）

任务卡 [#986](https://github.com/T-Auto/dsh-ops/issues/986)，叠在本真值表分支之上。本附录
记录 D2 锁定的内容，并按保守取向解决签字决定项 2 的优先级问题；全量档的发布仍归 D3。

**键。** `ptc` 与 `ops-ptc` 行接受 YAML-only 的
`disclosurePolicy: 'on-demand' | 'full'`（缺省 `'on-demand'` = 本表的旧路径，逐字一致）。
非法值报错点名键与收到的值或类型；非 PTC 行（`minimal`、`standard`、`cordis`）以
`disclosurePolicy applies to the ptc and ops-ptc rows only` 拒绝该键。内置消费者计划切片
与自定义 integration 在 D3/D4 学会该档位之前保持旧缺省。

**签字决定项 2，按 #979 §4 取保守解。** 显式全量选择是**独立的 opt-in**，绝不压过总
开关：`global.dynamicTools` 关闭期间全量档不生效——该行保持本表第 2 行的旧
resident/alwaysLoaded 面——而已保存的选择原样留在行配置里，开关回开后重新生效。这使
§4 的每条保证都成立：升级、保存设置与开关翻转从不写入或抹掉该键，操作者的关闭对
一切披露形态保持绝对。行级 `dynamicTools` 保持只管 loader 的含义：全量档不发布
loader（#979 §2），因此同时关掉 loader 的行保留自己的显式档位。该门编码在
`effectiveMode`；保存的意图与现有 dynamicTools 与门一样原样保留。
此为保守解，维护者可改。

**序列化。** `hostConfig`（保存路径的序列化器）逐字保留显式选择，且从不自动写键：
读取 → 保存一项无关设置 → 再读取，`'full'` 不丢；包括本表五行在内的每个旧输入在
raw 与序列化两层都保持该键缺席。

**仍未实现。** 真值表 T 行仍是目标：尚无任何路径发布全量档（D3 负责
`src/publication/ptc.ts` 与内置计划切片），没有设置页入口（D5），签字决定项 1、3、4
维持上文原状。

**验证。** `npm run build` 后 `node test/run.mjs ptc-disclosure-policy`——8 项检查，
先红（未实现基线上 8/8 失败，键被拒绝为 unknown），实现后全绿。
`node test/run.mjs ptc-config-truth` 13/0/0、`node test/run.mjs resident-switch`
24/0/0、`node test/run.mjs settings-rows` 14/0/0 在新解析路径上不变，worker 用
`DSH_OPS_WORKER_BIN=runtime/linux-x64/dsh-ops-worker`（sha256 2b5f988d）。


## D3 附录——显式全量档已发布（2026-11-19）

任务卡 [#987](https://github.com/T-Auto/dsh-ops/issues/987)，叠在 D2 附录的分支之上。本切片
把已解析的键变成发布行为；上文五行旧路径不被改写，仍由套件逐字断言。

**T 行，已实现。** `{ disclosurePolicy: 'full', allowedTools: [grep, stat] }` 的首轮发布
`ops_grep`、`ops_stat`、`ops_inspect_local_file`（常驻）与 `ops_result`，且没有
`ops_load_sdk`（#979 §2）。第一个程序即可直接调用获准池（双重验证：稳定声明集合 +
经 worker 的真实 `run_code` 绑定调用）；池外业务 API 仍不可用。内置计划切片现在携带
解析出的档位（`src/presets/builtin.ts`），发布在 `src/publication/ptc.ts` 消费它。

**签字决定项 1，按 #979 §3 取保守解。** 全量档首轮发布 `ops_result`：本步落盘的 ref
必须仍然可消费，且统一验收口径逼出同一结论——按需档永远可以加载 `result`
（`loadable = [...allowedTools, 'result']`），因此只有全量档也发布它，加载完毕的业务
集合才等于全量首轮集合。该对比由一项检查钉住。

**边界，随实现一并断言。** 空上限使档位停在 常驻 + `result`（仍无 loader）。只读仍把
一切变更 API 从首轮剔除——切换档位绝不放宽权限。`residentTools:false` 丢掉常驻面
（第 5 行）但不丢显式档位。重复名收敛为一次注册。总开关保持 D2 的否决，端到端成立：
`global.dynamicTools` 关闭期间显式全量行逐字发布第 2 行；行级 `dynamicTools` 保持
只管 loader 的含义，因此同时关掉 loader 的全量行保留自己的档位。

**本切片刻意不做。** 自定义 integration 在 D4 之前保持旧缺省，
`PtcConfig.disclosurePolicy` 也因此保持可选（改为必填会迫使本卡触碰不属于它的
自定义 integration 计划切片；内置计划携带该值，缺省值即 on-demand）。设置页入口归 D5。

**验证。** `npm run build`，先红：`node test/run.mjs ptc-declaration-surface`
5 项中 4 项失败（全部新 T 行断言；旧 loader-less 检查保持绿），
`node test/run.mjs ptc-full-disclosure` 在套件 120 秒截止前 T 行、对比、只读与空池
均失败。实现后全绿：ptc-declaration-surface 5/0/0、ptc-full-disclosure 8/0/0，
回归锁不变——ptc-config-truth 13/0/0、resident-switch 24/0/0、
ptc-disclosure-policy 8/0/0、settings-rows 14/0/0；worker 用
`DSH_OPS_WORKER_BIN=runtime/linux-x64/dsh-ops-worker`（sha256 2b5f988d）。环境备注，
非回归：`ptc.test.mjs` 的安装包解析检查断言优先于 `DSH_OPS_WORKER_BIN`，因此该项
在不设该环境变量时运行（在基准 commit 上设同样的变量，失败方式相同）。


## P5 附录——四行准入判定，在注册、声明与分发三处对齐（2026-11-19）

**问题（#997；原始复现在 #968）。** 注册表里的定义不等于本步可调，但所有拒绝读起来
一模一样：PTC 分发层一律 `POLICY_DENIED`（"must be admitted"），发布源一律
`PUBLICATION_GRANT_UNAVAILABLE`，最糟的是 `ops_load_sdk` 对只读所禁的池内名
答 `INVALID_ARGUMENT: API is not in this scope's allowed pool`。模型分不清未加载
与被禁，已撤销的准入与从未存在的名字读起来也相同。

**四行判定，一个分类器。** `src/publication/ptc.ts` 对被拒分发恰好答四者之一，
与注册准入和 SDK 声明对齐：

| 判定 | 条件 | 应答 |
| --- | --- | --- |
| 本步可用 | 常驻或已加载，且获准 | 正常分发；不进拒绝路径 |
| 需加载 | 在池内、获准、未加载——且 loader 存在 | `SDK_NOT_LOADED`，点名 `ops_load_sdk` 与原始名，下一步生效 |
| 权限禁止 | 沙箱策略不允许该 API | `POLICY_DENIED`，明确权限措辞，不给加载建议 |
| 已撤销 | 曾存在的准入被撤——作用域被撤、呈现被收回、或已可用 API 权限被降级 | `POLICY_DENIED`，撤销措辞，与其余三者都不同 |

过期或外来绑定保持原有的普通准入拒绝，四行之外没有新承诺。只有 loader 真的能选时
才给加载建议：无 loader 作用域与全量档保持诚实的「无 loader 可选」拒绝。
`ops_load_sdk` 本身改为按配置池校验，并把权限拒绝从池拒绝中拆出——只读下的
`write_file` 是「权限不允许」而非「不在池内」；池外名保持 `INVALID_ARGUMENT`。
`SDK_NOT_LOADED` 拼写刻意沿用 OPEN PR #1007，让最终合并读起来一致；该 PR 的
deferred 指针管线仍归其所有。

**源层保持同一区分。** 被拉走的 registrar 授权答新码 `PUBLICATION_GRANT_REVOKED`，
不再读作「从未可用」；从未持有可用授权的 agent 保持
`PUBLICATION_GRANT_UNAVAILABLE`。授权与池语义未动——变的只有拒绝判定。
