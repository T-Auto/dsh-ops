# OPS 常驻内核：设计与证据

English: [Resident OPS kernel: design and evidence](resident-kernel.md).

本文跟踪 [#872](https://github.com/T-Auto/dsh-ops/issues/872)，源码审计基于 `e7244444`，记录完整目标及其所需证据。
显式常驻 transport 及其测试只证明下文所述实现；本地 Native/PTC 文件路径已迁入，持久 shell 与完整验收报告仍待完成。
所有未经验证的要求仍标记为待完成。

## 目标与所有权

每个实际运行的 DSH 实例只拥有一个 OPS 内核。插件激活时启动，握手成功后才发布可执行入口；
卸载或 DSH 退出时停止接单、取消所属执行并释放资源。内核空闲不退出。状态属于插件实例，
不能放在按用户、home 或工作区索引的模块全局单例中。

内核分派现有文件操作，拥有独立的会话 shell，以及登记到 DSH jobs 的显式后台任务。
Native 与 PTC 共用执行路径，同时保持各自结果投影。此方案替代摇篮/可重启 worker/空闲回收设计，
不新增监督器、透明重连、接管、重放或崩溃恢复系统。内核失败后须通过显式插件重启建立新实例，
旧 shell 状态不恢复。

DSH subprocess 所有权构成外层进程边界，私有 IPC 也归属这一生命周期。
Windows Job 所有权与宿主断连回收必须通过公开宿主接口证明。shell/task 内部终止所需的平台代码
集中在一个进程模块，禁止 breakaway/detach。常驻内核的权限不代表会话 shell 可以直接继承该权限。

## 显式 serve transport

worker 现在通过继承的私有控制管道提供显式 `--serve` 模式。作用域内的宿主客户端只启动一次，
等待 `ready`，关联 `started` 与 `completed` 事件，并按请求 ID 发送取消。最多准入 32 个活动请求，
请求与响应帧均有界，不重连、不重放失败调用。客户端先确认进程退出，再结束受中断的请求；
无法确认回收时明确报告 unknown。主入口先启动 provider，再发布 Native/PTC 文件工具；
本地文件请求复用它。已启用入口的 binary 选择冲突时在启动前拒绝。

文件操作可能阻塞在操作系统 I/O，因此每个已准入请求在内核的可信子进程中复用现有一次性
dispatch，并拥有独立终止句柄。Windows 子进程使用嵌套 Job；POSIX 子进程保留宿主所有的进程组，
定向取消使用尚未回收的子进程身份。这些固定文件 worker 不启动后代。请求运行期间控制循环
仍可响应，请求 deadline 只退出对应 worker。输出收集保留有界尾部并明确标记丢失。
EOF 与关闭会取消并等待已准入执行结束，不 detach、不重启 worker。

本地文件 dispatch 已消除重复的**宿主 runner** 启动；每次文件请求仍有原生子进程启动成本。
WSL 读取、受约束的 PTC batch/result 操作保留原有 runner，不能用可信本地文件路径
替代它们的强制执行上下文。最终 A/B 报告必须实测这些成本。这条 transport 不代表会话 shell、DSH jobs、完整多进程回收
或性能目标已经交付。

所属结果缓存清理复用同一常驻连接及既有类型化 `result/purge` 操作，不再启动公开的一次性 worker。
会话销毁先停止并等待其结果工作，再清理缓存；provider 退出也先封闭新工作，等待待完成的会话清理，
最后关闭连接。这覆盖宿主不等待的 Session 通知，以及共享显式 provider 的独立消费者。
既有生命周期按所有者顺序执行缓存 purge，因此大量 Session 通知同时到达也不会挤满准入窗口；
普通文件工作及其他所有者仍独立。四十会话回归覆盖未改变的 32 请求客户端上限，拒绝的 purge
也会释放后续清理。

provider 仅在该清理屏障期间保留公开 sandbox 与 policy 依赖。每次 purge 重新解析当前策略，拒绝
只读或已变化的权限，并将 Windows 当前私有临时目录授权与原来的根路径及 SID 比较。原生存储校验、
no-follow 目录、有界缓存名称和稳定会话锁均保持不变。普通准入关闭后，只有构造固定 purge envelope
的方法可以继续使用尚有所属的连接。provider 缺失/失败、授权变化或不完整回执继续保留既有延后清理
记录，不创建替代 worker，也不重放业务操作。

`resident-result-cleanup.test.mjs` 通过主入口及共享独立集成，使用真实 Agent/Session、策略、sandbox
和 subprocess 服务。每种路径从文件调用到销毁都仅启动一个公开内核进程；测试主动暂停清理，证明
退出会等待，并观察两个所属缓存均在内核退出前清除。另一个测试将缓存会话目录替换成链接，验证原生
拒绝且外部目标不变。这些是所有权/安全检查，不是性能测量，也不证明 #872 其余验收要求已完成。

Windows 验证覆盖十个相关套件、89 项检查，零失败、零跳过。在独立编译副本中仅移除保留权限依赖的
hook，主入口检查即失败：两个缓存均未完成清理；独立集成和 no-follow 检查仍通过。四十会话测试最初
仅完成 32 次 purge，加入生命周期顺序清理后通过。仅移除客户端重复 drain 调用不会失败，因为保留依赖
的 disposer 也会等待清理。夹具准备失败及这个无效反例与有效反例分别保留，不算作生产回归。

独立集成须先在共同所有者的激活作用域中显式挂载 `residentKernel()`，再挂载消费者，详见
[集成设置](集成接口.md)。移除单个消费者不销毁共享 provider；移除 provider 会撤销依赖的文件发布，
保留的调用方直接失败，不启动替代进程。纯外部 discovery 保持独立生命周期，不要求 OPS 内核或文件权限服务。

## Rust 可复用边界

| 源码 | 当前行为 | serve 入口的要求 |
| --- | --- | --- |
| `native/src/main.rs::main` | 从 stdin 读到 EOF，最多 2 MiB + 1；解码一次，输出一份带换行的 JSON。 | 添加明确的 serve 分帧；不能把当前 main 直接套进循环。旧一次性格式须明确分离。 |
| `native/src/main.rs::main` deadline 线程 | 休眠到解码后的 timeout，再调用 `process::exit(124)`；线程仅随一次性进程终止。 | serve 不能使用该机制；旧请求的计时器不能杀死后续请求或整个内核。 |
| `native/crates/ops-protocol/src/envelope.rs` | 校验版本、requestId、component、storage 和 budget；请求最多 2 MiB，结果 maxBytes 为 1–128 KiB，原始默认超时 300 秒。 | 复用真实边界校验和保持副作用事实的编码；事件显式带 ID，帧开销计入输出预算；坏 serve 帧不得降级为旧格式。 |
| `src/execution/protocol.ts::workerEnvelope` | bridge 请求最多 30 秒、128 KiB 输出。 | 这是请求预算，不是五分钟内核空闲回收规则。换 transport 时保留对应预算。 |
| `native/src/lib.rs::dispatch` | 校验/规范化 root、打开本次请求目录句柄、计算 root identity、调用能力并完成 spill。 | 可信准入后复用该入口；不要把文件业务行为写入 transport。 |
| `native/crates/ops-protocol/src/lib.rs::Request` | 持有权限字段、输出预算、storage 与 `Rc<OutputSink>`，没有取消/deadline 上下文。 | 增加请求所有的一个强类型执行上下文。Request 不是 Send；可在执行线程内解码，避免把所有局部 capture 改成共享锁。 |
| `native/crates/ops-protocol/src/capture.rs::OutputSink` | 使用请求局部 RefCell，capture 预算接近 10 MiB。 | 保持 capture 局部；transport 另需有界缓冲，capture 配额本身不提供流背压。 |
| `native/crates/ops-search/src/scan.rs::Scan` | 在扫描/读取步骤之间检查自身 30 秒 deadline；索引枚举接收剩余扫描时间。 | 将操作上限与请求 deadline/取消结合，保留 partial 覆盖及无游标规则；无法中断已经阻塞的 OS 调用。 |
| `native/crates/ops-files/src/file.rs::read_bytes/stream_facts` | 文本整读最多 32 MiB；hash 流式读取完整文件，没有取消检查点。 | 在有界块之间检查；stat 会 hash 内容，不是廉价且按文件大小有界的纯 metadata 操作。 |
| `native/crates/ops-files/src/file_prefetch.rs::load` | 最多两个 scoped 读取线程，随后 join。 | 当前父请求取消不能停止阻塞读取；不能遗弃线程，让其超出所属执行的生命周期。 |
| `native/crates/ops-documents/src/lib.rs`、`xml.rs`、`pdf_text.rs` | 表格/XML/PDF 各有独立 30 秒检查，解析与 IO 同步。 | 传递同一个请求取消/deadline，同时保留文档自身上限与 partial 事实。 |
| `native/crates/ops-files/src/file_single.rs::authorize_write` | no-follow 路径校验后检查 read-only/write_roots；变更保留 CAS/发布回执。 | 保留校验与发布边界；取消不能把可能已发布的写入改成 effectState:none。 |
| `native/crates/ops-batch/src/lib.rs::execute` | 操作前先记录 State::Unknown；未确定的副作用只验证，不盲目重复。 | 保留审计行为；它不授权自动重放，也不替代 DSH jobs。 |
| `native/crates/ops-results/src/spill.rs::finish` | 形成有界输出，并可能写私有结果缓存，包括可写会话中的观察工具。 | “只读工具”不等于零缓存副作用；初始无写入探针应明确 read_only=true 且不传 storage。 |

`src/execution/files.ts` 明确使用可信、仅接收数据的文件执行模型，而不是任意代码沙箱 runner。
它取得会话策略、解析路径、填充 read_only/write_roots/凭据拒绝根，并在异步准备后复核权限。
模型参数不是权限来源。常驻文件路径必须保留此模型；shell 则须取得独立有效的宿主 confinement。

## 请求生命周期约束

执行或输出阻塞时，控制读端仍须能接收取消。有界帧读取与有界结果写入可承担这一职责，不能无限
创建线程、使用无界队列或缓冲整个会话 stdout。每个 requestId 只能有一个终态回执，重复 ID、
终态后的取消与不完整帧均须有明确行为。私有连接承载宿主可信上下文，命令 stdout/stderr 是独立
数据面。具体帧 schema 与上限由实施切片定稿。

Rust 中 deadline 与取消标记应随一个请求执行上下文传递，在执行前、有界工作单元之间、以及安全的
发布前边界检查。提交点之后保留已知 applied/partial 效果；无法确定发布状态时返回 unknown。
发送“已接收取消”回执并不证明工作已经停止。

协作检查无法中断全部文件系统 syscall、解析器或平台操作。无界/可能阻塞单元迁入前需要独立可终止
范围，否则应明确留在常驻热路径之外。为一个请求杀死整个内核、遗弃线程、或者写入仍在继续却返回
“已取消”，都不是替代方案。目前进程级取消提供的保证，常驻 dispatcher 还没有。

只有权限边界、IPC、持久化数据与 OS 结果需要边界校验；内部使用强类型上下文和直接调用，不新增
并行的 guard/lease/seal 体系。执行状态分别属于请求、会话或实例；不可变代码常量和已有凭据匹配
表达式缓存不属于执行所有权。

## 公开宿主能力待核验项

生产 transport 选型之前，宿主探针必须回答下列问题；Rust 源码审计不能单独证明。

| 问题 | 状态 |
| --- | --- |
| 公开 subprocess 是否能启动一个持续双向通信、具有可用流读写端的进程？ | Windows/WSL 的 Node 夹具及 Windows Rust 探针均通过 `stdio.control:'pipe'` 和 `SubprocessHandle.control` 验证。Windows 原生 fd 7 通过下述六项检查，其他原生平台仍待验证。 |
| stdio 不适用时，能否只在启动时创建私有 IPC 端点，并绑定宿主拥有的进程生命周期？ | 公开继承控制通道与 stdout/stderr 分离；夹具证明分离并使用有界帧/队列，无需外部 socket 服务或每次请求 runner。 |
| 卸载、强制宿主死亡、控制断连、内核崩溃能否在 Windows/POSIX 回收后代，且无 breakaway/detach？ | Windows 六项全部通过；WSL 使用 provider 进程组 fallback 时五项通过，阻塞内核下宿主 SIGKILL 后仍有两个存活休眠进程。Linux 原生 systemd-scope 所有权尚未测试。 |
| 宿主是否能对常驻父进程下独立取消的 shell/task 执行单元应用所需 confinement？ | 待验证；必须保留真实沙箱保证。 |
| 显式任务发布/回收能否复用公开 DSH jobs，且无重复所有权和取消交接空隙？ | 待任务集成切片。 |

公开接口不能提供某项保证时，记录具体缺口与决策，不能使用 bare spawn、私有宿主补丁、放宽
confinement 或额外服务绕过。

### 公开宿主探针证据

安装固定依赖后运行 `node bench/probes/probe-872-host.mjs`。这是模拟 Node 内核及普通非 detached
子进程，不是 Rust serve 实现。所有内核均通过公开 `ctx.subprocess.spawn` 启动；raw spawn 仅用于
可销毁的测试宿主及模拟 shell 子进程。子进程继承同一个外层拥有范围。

固定的 `@deepseek-ai/dsh-subprocess` 版本为 `0.2.2-rc.1`，公开类型提供控制管道创建、Duplex
端点、`terminate()` 和 `waitForExit()`。Cordis 提供 `ctx.root`（实验性）和异步 `ctx.effect`
回收。夹具把所有权保存在各插件闭包中，验证卸载一个根后另两个仍可运行，并验证普通 stdout/stderr
不进入控制结果。帧最多 64 KiB、接收队列最多 16 项；该冒烟探针不替代恶意协议/背压测试。

| 平台 | 实测结果 | 证据范围 |
| --- | --- | --- |
| Windows，Node `v26.12.1` | 六项通过；75 次只读夹具请求只启动三次内核；无需紧急回收。消费者卸载、响应/阻塞状态控制断连、内核硬崩溃，以及响应/阻塞内核下宿主 SIGKILL，均回收普通后代。 | 尚未测试 Rust 内核、持久 shell、breakaway 后代或创建进程到加入 Job 之间的崩溃窗口。 |
| WSL Ubuntu，Node `v24.11.1`，进程组 fallback | 五项通过；内核事件循环阻塞时宿主 SIGKILL，内核 PID 641 和 leaf PID 648 超过十秒截止仍存活；观察者显式紧急回收。两者 `/proc` 状态均为 `S`，进程组/session 均为 641，cgroup 均为 `0::/init.scope`。 | 本轮所有内核均留在 `/init.scope`，证明没有进入原生 `dsh-subprocess-*.scope`。可访问的 user manager 本身没有使 provider 选择原生后端，具体原因尚未确定；原生 systemd-scope 行为尚未测试。 |

Windows 源码提供独立宿主死亡路径：私有 Job runner 的 IPC `onDisconnect` 调用
`releaseOwnedJob`（`dsh-subprocess-local/lib/runner.js`），Job 使用 `KILL_ON_JOB_CLOSE`
（`dsh-win32-process/lib/index.js`）。这是宿主实现证据，不是 OPS 可调用的私有接口。Linux
`scopeArgs` 创建 user scope，没有宿主生命周期绑定；`terminateForHostExit` 由 JavaScript
`exit` 监听器触发。provider 可能 fallback，公开 handle 也不暴露实际选中的 containment 能力。

因此，POSIX 原生内核需要独立于 dispatch 和输出的控制 EOF 监听线程，集中回收所属进程，且须在
dispatch 阻塞时实测该路径。静默、心跳和页面断开均不是死亡信号。阻塞 Node 夹具测试的是更强的
“仅靠宿主回收”能力；失败不表示 #872 不可实现。Windows 原生控制访问已有下述实证；dispatch
阻塞时的原生回收、后代回收、confinement 和内核硬崩溃仍须分别提供可运行验收证据，再选择生产架构。

### 原生控制与 dispatch 探针

先运行 `cargo build --locked --manifest-path native/Cargo.toml --example resident_probe`，再运行
`node bench/probes/probe-872-native.mjs`。该 example 是显式兼容性探针，不是生产 worker 的 serve
入口，也不是插件激活路径。它仅接受无 storage/cache 授权的只读文本 `inspect_local_file`，复用
现有 dispatcher。

`native/crates/ops-process` 将平台 IO 隔离在禁止 unsafe 的 core 之外。POSIX 复制继承 socket
并设置 close-on-exec；Windows 解析 CRT 描述符 7，复制为不可继承的 OS handle，再通过 CRT 关闭
原始描述符。宿主管道采用异步模式，因此 Windows 读写使用 overlapped IO 及每次操作独立事件。
helper 复用已锁定的 `libc 0.2.190` 和 `windows-sys 0.61.2`，没有新增解析的外部包。

Windows、Node `v26.12.1` 实测六项通过：25 次关联检查只使用一个原生进程；拒绝可写执行；控制
EOF 无需宿主 terminate 回调即可退出；坏 JSON 结束探针；超过 64 KiB 帧上限的输入结束探针；
没有继承控制通道时以错误干净退出且不发握手。普通 stdout 分离另有断言。helper 与 example
单元套件各一项通过；helper all-targets Clippy 在禁止 warning 下通过。CI 已配置在四个发布平台
构建并运行原生探针；[PR #901 CI](https://github.com/T-Auto/dsh-ops/actions/runs/43429421444)
已通过全部四个平台，包含此兼容性探针。

探针的独立读线程在 dispatch 之外接收控制 EOF；只有一槽等待队列，过载则结束探针，并非生产准入/
背压协议。握手明确标记尚不支持请求取消和 deadline 执行。EOF 结束整个只读探针，不是单请求取消
实现。这六项检查不证明 dispatch 阻塞、后代回收、宿主强制死亡或插件卸载。新的显式 serve 实现
及本地文件集成见上文；持久 shell、任务 jobs 与完整验收仍待完成。

## 实施切片与退出证据

它的一次性执行子进程仅在 stdin EOF 后写出 PID 回执，再固定阻塞十分钟。测试开关或环境变量
钩子不进入已发布 worker。探针使用生产客户端与固定版本的公开 subprocess provider，证明可以
只结束一个阻塞请求，同时保留另一阻塞执行和快速请求；断连、内核崩溃及 provider 卸载也须回收
所属执行且不重放。观察者记录精确 PID，在紧急清理前检查幸存进程。Windows 四项均通过，
无幸存进程；CI 在四个发布平台运行同样检查。报告保存在 `bench/runs/blocked-resident-*`。

## Windows shell 进程基础层（C1）

`ops-process::shell` 新增仅适用于 Windows 的所有权与 I/O 基础层，由
`native/examples/shell_range.rs` 和 `bench/probes/probe-872-shell-range.mjs` 实际调用。
已发布 shell 工具仍使用原执行路径。本切片不代表持久命令完成协议、会话队列、后台任务、
权限重新准入或最终性能目标已实现。

调用者传入公开 sandbox provider 返回的原样 argv，以及从公开 `scrubbedParentEnv()` 开始
构造的完整显式环境。原生模块不解析权限策略，也不继承常驻内核的环境；拒绝相对 executable、
无效 Windows 参数和重复环境名，并移除继承的 control 标记。`CreateProcessW` 同时使用
`CREATE_SUSPENDED`、仅包含 stdin/stdout/stderr 的显式句柄列表，以及原子的
`PROC_THREAD_ATTRIBUTE_JOB_LIST`，再恢复主线程。stdin 默认为 EOF。嵌套 Job 设置
kill-on-close、禁止 breakaway；包括 detached 子进程在内的后代都属于该范围。隐藏私有
console 与其他 shell console 隔离。

每个私有通道使用随机名称、最多四个预先创建的 pipe instance、固定 pipe buffer，并以最多
128 KiB 的可配置前缀限制保留输出；达到保留上限后仍持续排空并统计观察到的字节数。
受保护 ACL 只授予 owner/SYSTEM 和当前 logon SID，并设置 Low mandatory label，
不授予 Everyone 写权限。接收端在接受字节前检查实际 pipe peer 是否属于目标 Job，
并关闭被拒绝或已结束的 instance。无法观察身份属于通道错误，不代表输出完整。
确认 Job 清空后，`drain()` 封闭未使用的连接，等待已接纳 writer 的真实 EOF；超时即错误。
`close()` 表示中止，不是完成凭据。普通进程 stdout/stderr 也独立有界并持续排空。

软中断使用固定、可信、仅在取消时启动的 executable entry point。controller 自身通过同一
原子范围 launcher 启动，显式环境为空，凭据有界并有截止时间；成功、超时和失败都会等待其
回收。只有这个一次性进程调用 `AttachConsole` 和
`GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)`，发信号后直接退出，不再调用 `FreeConsole`。
常驻内核从不改变自己的 console 或 handler。Windows 异步投递 console 信号，而
[FreeConsole 会重置 handler table](https://learn.microsoft.com/en-us/windows/console/setconsolectrlhandler)；
早期内核内实现曾稳定在下一次 control 请求前以 `STATUS_CONTROL_C_EXIT` 退出。
当前探针保留发现该问题的后续请求及兄弟范围检查。成功的信号凭据仅表示尝试投递，
不证明目标配合；实际受限 wrapper 保留 ignore-Ctrl+C 行为，需要回收所属范围。

Windows 上使用完整、已验证的 Niubash payload 复现：

```console
npm run build
cargo build --locked --manifest-path native/Cargo.toml --example shell_range --example shell_signal_fault
cargo build --locked --manifest-path native/Cargo.toml -p ops-process --example shell_signal_cooperative
cargo test --locked --manifest-path native/Cargo.toml -p ops-process
node bench/probes/probe-872-shell-range.mjs <shell_range.exe> <pinned-niu.exe>
```

真实公开 sandbox 策略只授予新建的临时工作目录。当前 Windows backend 对两个受限模式均报告
`partial` enforcement；报告保留此事实，不声称绝对 confinement。默认固定 runtime 与依赖
版本未变，仅启用现有 `windows-sys` feature。该新基础层在 POSIX 上明确返回 unsupported，
因为新进程组可能逃离宿主 fallback 的所有权；现有 POSIX 执行不变。
原生进程组/cgroup 所有权仍需独立证明。

Windows 本地验证：公开宿主探针 **13 项通过**，包括后续两次协作式测试 shell 捕获 INT 并以 42
退出、受限模式的软中断尝试/硬回收、helper 超时与崩溃、兄弟范围隔离、内核硬退出、EOF
清理，以及四条独立流各排空 1 MiB 但仅保留 1024 字节；所有跟踪进程均已消失。
`ops-process` **17 项测试通过**，另有一个现存子进程夹具由 harness 忽略、由生命周期测试
显式调用。原生 workspace 测试成功退出。这些是 C1 结果，不是 #872 的完整验收报告。

INT 正向夹具先显式启用 Ctrl+C，再启动 Niubash；等待进程使用不会被子进程继承的 handler。
Git Bash/CI 可能传入继承的忽略标志，导致生产信号尝试成功后这个断言仍失败。生产 launcher
保留原有标志；目标忽略信号时仍需终止所属范围。PowerShell 和 Git Bash 都运行同一正向断言，
不会跳过或重试。
