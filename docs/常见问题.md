# 常见问题

装不上、报错看不懂、行为不符合预期时先查这里。

---

## 安装与载荷

### `node_modules/@dsh-ops/` 下没有 `bash-win32-x64`

**这不是安装损坏。** 三个载荷都是精确钉版的**可选依赖**（`optionalDependencies`）：若你的 registry 未同步该平台包的对应版本，包管理器会**静默跳过**它——安装仍以退出码 0 结束，且不打印任何指向缺包的警告。

实测（2026-10-12）：`registry.npmmirror.com` 上 `@dsh-ops/bash-win32-x64` 的 `dist-tags.latest = 0.0.0-stage`、`versions` 只有 `0.0.0-stage`；官方源 `registry.npmjs.org` 为 `0.2.1`。走镜像的 `npm view @dsh-ops/bash-win32-x64 version` 因此会打印误导性的旧版本号，不能拿来判断载荷是否可用。镜像补齐后本节自然过期，下面是自证与兜底的办法。

**首选兜底**：`provision-shells` 绕过 registry，直接取上游 GitHub Release 的钉版资产，校验 sha256 后解包，并写 `.provisioned.json` receipt。

```console
npx --yes dsh-ops@latest provision-shells --bash
```

需要代理时（`HTTPS_PROXY` 会被显式交给 curl 的 `--proxy`，同时随环境继承）：

```console
:: cmd
set HTTPS_PROXY=http://127.0.0.1:<clash-port>
npx --yes dsh-ops@latest provision-shells --bash
```

```console
# PowerShell
$env:HTTPS_PROXY = 'http://127.0.0.1:<clash-port>'
npx --yes dsh-ops@latest provision-shells --bash
```

**核对**请跑 profile 自己那份副本：`ladder` 只报告**执行它的那份包**的随包梯级，`npx … ladder` 检查的是 npx 缓存副本，结论与你的 profile 无关。

```console
node "%USERPROFILE%\.dsh\profiles\<profile>\node_modules\dsh-ops\bin\dsh-ops.mjs" ladder
```

provisioned 副本在 `<DSH_HOME>/dsh-ops/shells`（跨 profile 共享，provision 一次对同机所有 profile 生效），解析时优先于随包副本，`ladder` 会给出 `source: provisioned`。

**不要**用 `allowSystemShellFallback: true` 绕过：那是安全姿态降级（改用未固定摘要的系统 bash），且首次升级启动的配置迁移会把它改回 `false`。

### 缺少随包 bash 载荷时 `ops_bash` 的报错

当随包 bash 载荷在 profile 的声明/lockfile 中存在、但实际 `node_modules` 已被宿主包管理器清理时，`ops_bash` 会返回可读的 `ENOENT` 诊断，而不是把裸的 `spawn` 异常抛给模型。此时应使用 profile 的 frozen install 或官方插件管理器恢复依赖；不会静默切换到未授权的系统 bash。

## 命令执行

### 整轮因 `MALFORMED_RESPONSE` 作废

长脚本、heredoc、多层引号与反斜杠会让模型在工具调用 JSON 里做多层转义。请先用宿主的文件工具把脚本写入文件，再传给 `script_path` 执行，不要整段塞进 `command`。详见 [使用指南](使用指南.md)。

### 把 `run_in_background` 传给 `ops_bash` 被拒绝

**`ops_bash` 没有 `run_in_background`，也没有 job id**，命令一律前台执行。宿主 `bash` / `pwsh` 工具接受该参数，所以模型容易套错。常驻进程请改用宿主 `pwsh` 工具的 `run_in_background`，或在命令内部自行脱离（如 `nohup ... & disown`）。否则该次调用会一直占用到 `timeoutMs`（上限约 24.9 天）。

### 参数被判为未知键

`ops_bash` 的 schema 不声明的键会在执行前被拒绝，错误信息会同时点出未知键与可接受的键。这是刻意的——不会静默忽略。

### 受限模式下 `ops_bash` 无法运行自定义 bashPath 或 Git for Windows

现象（只读或工作区内修改会话）：`EXECUTOR_UNAVAILABLE: ops_bash cannot run the configured bashPath … in restricted modes`（0.3.0 时报 `This MSYS version has no verified DSH IPC compatibility build. Rebuild the matching proxies`）。

**这是按设计的行为。** 在 DSH 的 Windows 受限令牌下，MSYS 无法创建自己的 signal pipe（`couldn't create signal pipe, Win32 error 5` / `0xC0000142`）。dsh-ops 通过针对某一个固定摘要 `msys-2.0.dll` 校验过的 IPC 兼容代理让 Bash 在受限模式下可用；其它任何 MSYS 版本——自带 Git for Windows、自定义 `bashPath`、`allowSystemShellFallback` 找到的系统 bash——都会被拒绝，而不是裸执行。重建代理不是终端用户的补救办法：`npm run build:bash-ipc` 只会重新固定随包载荷。

处理办法：

- 从 `dsh-ops/shell` 行删除 `bashPath`（以及 `allowSystemShellFallback`），改用随包的固定摘要 bash；若该载荷缺失，运行 `npx --yes dsh-ops@latest provision-shells --bash`。
- 或者把会话切换到 `danger-full-access`，此时 `bashPath` 会直接运行。
- 用 profile 自己的副本检查：`node "<profile>\node_modules\dsh-ops\bin\dsh-ops.mjs" ladder --config <文件>`，报告中的 `restricted: yes/no` 表示受限模式能否运行所选 bash。

### `ops_bash` 拒绝 `sandbox_permissions` / `justification`

宿主 `bash` 工具支持单次调用升级；`ops_bash` 不支持，错误信息里会写明这一点。请让用户切换会话权限模式，而不是重试该调用。
### 文件工具收到空占位参数

严格的工具调用适配器会把 schema 里每个字段都填上，于是 `ops_inspect_local_file`、`ops_grep`、`ops_glob`、`ops_replace` 未使用的可选字段会收到 `""`、`null` 或 `[]` 占位值。插件会在原生 worker 运行前丢弃这些可选字段的占位值，不再触发 `path`/`encoding`/`view` 校验报错。必填字段、`replacement: ""`、`false` 和 `0` 仍原样转发，真正非法的值依旧会报错。

## 权限与沙箱

### 用过 OPS 文件工具后，宿主 `edit` 报「has not been read」或「changed since it was read」

此改动后已修复：`ops_inspect_local_file` 与 `ops_replace` 会像宿主 `read`/`edit` 一样登记到宿主的「先读后改」观测表，之后宿主 `edit` 可直接使用。旧版本（基于 FastCtx 的 0.2.x）中 OPS 的读取不计入观测，使用宿主 `edit` 前请先用宿主 `read` 读一次。（#17）

### 文件工具是否需要命令权限

不需要。固定文件操作走 DSH fs-sandbox 同类的可信操作权限检查，**不执行模型代码**。read-only 拒绝替换，workspace-write 允许工作区与 DSH 临时区域内的读与替换，full-access 不额外限制路径。临时区只在既不是文件系统根、也不包含用户家目录时才计入。

### 后台工具为什么开启后仍不可用

`dsh-ops/background` 组件开启后，仍须会话权限为 `danger-full-access` 才发布四个后台工具。

### `DSH workspace preparation failed`

在工作区内修改会话中，第一次受限 `run_code` / `pwsh` / `bash` / `ops_bash` 调用前，dsh-ops 会给工作区根目录补一条仅作用于该目录的 `WRITE_OWNER` ACE（宿主沙箱需要），并先把原 DACL 备份到 `<DSH_HOME>/dsh-ops/acl-backups/`。之后的调用走很快的 `ready` 路径。

这一步用 Windows PowerShell 5.1 运行包内自带的 `bin/prepare-workspace.ps1`，**以当前用户身份、在沙箱约束生效之前执行**；只在 Windows 的工作区内修改模式下运行，且只修改工作区根目录自身的 DACL。只读与 danger-full-access 会话会跳过它。

报错会写明原因：

- `PowerShell execution policy blocked dsh-ops's own preparation script …`：dsh-ops 会传 `-ExecutionPolicy Bypass`（旧版本没有传，因此 Windows 客户端默认的 `Restricted` 会让所有 shell 工具失败，#66）。现在仍被拒绝，说明是组策略（MachinePolicy/UserPolicy）在强制执行策略，`Set-ExecutionPolicy -Scope CurrentUser` 无法覆盖。请运行 `powershell.exe -NoProfile -Command Get-ExecutionPolicy -List` 检查、联系管理员，或为该会话使用 danger-full-access。
- `the workspace root … does not meet the sandbox prerequisite …`：问题出在文件夹本身——不属于当前用户、路径经过 junction 或符号链接，或 `WRITE_OWNER` 被显式拒绝或无法授予。请修正该文件夹的所有者或权限，或打开你自己拥有的工作区。这不是 DSH 的授权拒绝。

- 根目录 DACL 通过它自己的句柄写入，不触发 Windows 的继承遍历，耗时不再随文件数增长（实测 5 万文件 18.7 s → 4.3 s；10 个文件约 3.9 s，主要是 PowerShell 启动）。旧版本会遍历整棵目录树，大工作区触发 10 s 限制且冒号后为空。（#43）
- `the preparation executor timed out after 120000 ms …`：触发了 120 s 兜底超时。此时 ACL 状态未知，重试前请把根目录 DACL 与 `acl-backups` 中最新的收据对比。`the preparation executor could not start …` 表示 `powershell.exe` 本身无法启动。
- `exited with code N …: <文本>`：其它失败，附脚本自己的输出。

### 宿主 shell 被拒绝

`shellPolicy: deny-host-shell` 会拒绝 `deniedHostTools` 列表中的宿主 shell（默认 `[pwsh, bash, pwsh_persistent]`），该策略与 `allowSystemShellFallback` 独立。这也会禁用第三层 pwsh，谨慎开启。

## 安装位置与 profile

### `tui` profile 是什么

`tui` 映射到 **dsh-TUI 产品的 `dsh-tui` profile**，不是旧的 `tui` 目录。

### 桌面端为什么必须用它自带的 CLI

普通 DSH CLI 不能管理保留的 `desktop` profile；不要把它与桌面自带入口混淆。桌面端默认探测 `%LOCALAPPDATA%\Programs\DeepSeek Harness\resources\runtime\cli\bin\dsh.cmd`，装在别处时用 `--dsh-cli` 显式指定。

### 卸载后 `~/.fastctx/` 还在

默认不删持久状态；需要时显式加 `--purge-fastctx`。

### 旧版 provision 的文件没被清掉

旧版显式 provision 的 `<DSH_HOME>/dsh-ops/` 文件需单独清理：`npx --yes dsh-ops@latest uninstall --yes`。

## 进程

### `runtime-host` 进程是不是泄漏

不是。它是上游可复用的共享进程，父进程已退出不等于泄漏；无客户端且空闲约十分钟后自行退出。不要按进程名批量杀它。新版不自动清理旧版本已留下的进程。
