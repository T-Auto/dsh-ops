# Index-versus-walk A/B evidence (G4)

Chinese: [索引与遍历 A/B 证据](索引AB基准.md)。Design: [#584](https://github.com/T-Auto/dsh-ops/issues/584). Slice: [#614](https://github.com/T-Auto/dsh-ops/issues/614). Research question: [#423](https://github.com/T-Auto/dsh-ops/issues/423).

This document is the reproducible evidence for one question: **does the optional name index make
`ops_glob` faster than the walk on the same corpus and the same worker binary, and what does it cost
in memory?** It is evidence, not a performance gate. Nothing here changes a default, and no number
below is a CI threshold.

## What is compared

One corpus, one worker binary, one request shape. The two arms differ only in the trusted envelope
field the host adds when the operator turns on `indexCache`:

| Arm | request | host equivalent |
| --- | --- | --- |
| walk | no `cache_dir` | `indexCache: false` (the default) |
| index | `cache_dir: <dir>` | `indexCache: true`, cache prepared 0700 |

The request is a read-only `glob` with `limit: 10000` and `outputMode: paths`, so neither arm is
truncated by the page limit. The measured span is the worker process from spawn to exit: it includes
the fixed process-start cost both arms pay, and the indexed path's own work.

The harness is `bench/index-ab`, wired as `node bench/cli.mjs index-ab`. It uses the shipped binary
directly, so it does not need two profiles, an LLM, or a host build.

## Scope of the recorded run

At the recorded revision the platform sources are wired but **not Ready**: `ops-linux-index`'s
`Phase::Unwatched` reports `SourceState::Unsupported`, `ops-win-index`/`ops-mac-index` behave the same
until their watcher slices land, and `ops-search` falls back to exactly the walk on any state other
than `Ready`. The runs below therefore measure the **opt-in gate when it falls back**, not an
engaged index:

- identical bytes on every query are the expected result, and they are asserted;
- the timing difference is the gate's overhead, not a benefit;
- the memory delta is the extra code path, not a built index;
- the real A/B (warm snapshot, incremental watcher) must be re-run when L2/M2/W2 and the persistence
  store are wired, using the same command and the same recorded corpus hash.

Evidence for that state: `native/crates/ops-linux-index/src/source.rs` (phase table, `Unsupported`
for `Unwatched`), `native/crates/ops-search/src/index_source.rs` and the tests
`a_ready_source_produces_the_same_glob_output` / `a_cache_directory_without_a_ready_source_falls_back_to_the_walk`
in `native/crates/ops-search/src/index_source_tests.rs`.

## Corpus

Generated by `bench/index-ab/plan.mjs` from a fixed recipe: seed `0xA1B2C3D4`, 12 packages x 7
directories x 18 files plus root files, content length 48..4096 bytes. It contains `.hidden/`,
`node_modules/` and `target/` directories on purpose: the traversal contract excludes them, so their
presence proves the A/B did not expand the scan surface.

| fact | value |
| --- | --- |
| files / directories | 1,552 / 154 |
| content bytes | 3,159,745 |
| depth | 4 |
| excluded directories | `.hidden`, `node_modules`, `target` |
| tree sha256 | `6af8888faa0ec08dfdb4c376d24197ff6ee8ed0cb1654d721fcc441aadd018cd` |

The hash covers every relative path, its size and its content hash; it is the identity a later run
must reproduce. The engine is pinned in `plan.mjs`, not in this document, so the recipe cannot drift
silently from its description.

## Queries

| id | pattern | what it exercises |
| --- | --- | --- |
| ext-rs | `**/*.rs` | extension glob over the whole tree |
| basename-json | `*.json` | basename glob |
| nested-js | `packages/**/src/**/*.js` | deep anchored path pattern |
| name-mod-rs | `**/mod.rs` | repeated basename at arbitrary depth |
| no-hit | `**/*.nomatch` | full coverage scan with no hits |

## Method

1. Cold: the first call per query and arm (page cache is **not** dropped: that needs root, so this is
   first-touch, not a cold-cache measurement; the docs say so instead of pretending).
2. Warm-up: 2 discarded rounds per query and arm.
3. Measured: 9 rounds per query and arm, arm order alternating per round (AB/BA) so drift does not
   favor one side; the report keeps both the independent medians and the **paired** median of
   per-round differences.
4. Peak RSS from `/proc/<pid>/status:VmHWM` sampled every 2 ms while the worker runs (`n/a` when the
   process is too short to sample).
5. Pass/fail is byte identity between the arms on every call; a duration is evidence, never a verdict.

### Cold first call (ms)

| query | walk | index | delta |
| --- | ---: | ---: | ---: |
| ext-rs | 12.92 | 8.84 | -4.08 |
| basename-json | 11.93 | 10.90 | -1.03 |
| nested-js | 9.44 | 11.02 | +1.58 |
| name-mod-rs | 8.89 | 8.69 | -0.20 |
| no-hit | 14.31 | 13.48 | -0.83 |

One sample per arm: cold deltas are dominated by first-touch and process-start noise, which is why
they are reported separately and not used for the verdict.

### Warm repeated calls (9 rounds, p95)

| query | walk median | walk p95 | index median | index p95 | delta | paired delta | identical bytes |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| ext-rs | 13.51 | 17.21 | 13.81 | 15.51 | +0.3 | -1.98 | yes |
| basename-json | 11.77 | 16.01 | 13.68 | 16.26 | +1.91 | +1.43 | yes |
| nested-js | 13.84 | 16.65 | 13.24 | 18.23 | -0.6 | -0.32 | yes |
| name-mod-rs | 10.68 | 15.79 | 12.82 | 15.96 | +2.14 | +3.89 | yes |
| no-hit | 12.71 | 16.98 | 10.74 | 17.18 | -1.97 | +0.2 | yes |

Paired deltas range from -2.0 to +3.9 ms across queries with no consistent sign; both arms are
dominated by process start and the walk itself. The widest pair (name-mod-rs, +3.89 ms) is not
repeatable (its independent median delta was +2.14 ms while ext-rs and no-hit were negative), so the
run does not establish an index-side effect in either direction.

### RSS and budget

| query | walk median RSS (kB) | index median RSS (kB) | delta (kB) |
| --- | ---: | ---: | ---: |
| ext-rs | 3,944 | 3,988 | +44 |
| basename-json | 3,880 | 3,980 | +100 |
| nested-js | 3,884 | 3,980 | +96 |
| name-mod-rs | 3,932 | 3,968 | +36 |
| no-hit | 3,876 | 3,968 | +92 |

| budget fact | value |
| --- | --- |
| estimated index payload for this corpus (57 B/entry + name bytes + header) | 0.11 MiB |
| snapshot cap enforced by the persistence slice (`MAX_SNAPSHOT_BYTES`) | 256 MiB |
| headroom at this corpus size | 255.89 MiB |

RSS deltas are +36..+100 kB, consistent in sign with the extra code path but far below the 256 MiB
cap; no index payload is built in this stack. A 1,552-file corpus cannot exercise the cap, which the
persistence slice's own tests cover.

## Verdict

- **Output:** byte-identical on every cold and warm call of every query: the opt-in gate does not
  change an answer.
- **Warm latency:** no repeatable delta; paired deltas of -2.0..+3.9 ms on 10-14 ms calls and no consistent sign.
- **Memory:** no measurable index payload in this stack; delta +36..+100 kB, budget headroom
  255.89 MiB at 1,552 files.
- **Benefit:** not measurable today, because the index never becomes `Ready` in G3; claiming a
  speed-up from these numbers would be false.
- **Go/no-go:** keep `indexCache` opt-in and **do not enable it by default**. Go only after the
  watcher + persistence slices can answer `Ready`; then re-run this command, require byte identity,
  and require the warm median to beat the walk outside the paired noise band with an RSS delta
  inside the recorded budget. Until then the walk stays the only production path.

## The four #423 conditions, item by item

| condition | evidence |
| --- | --- |
| 1. Memory/RSS is bounded and compared with a budget | measured RSS table above, 57 B/entry and 256 MiB cap from `ops-index`/persistence, headroom table |
| 2. Authorization and identity are re-checked outside the cache | `walk_indexed` authorizes the root before the source is consulted; `candidates::revalidate` re-stats every candidate; `deny_roots`/credential-name policy applies on both arms; tests in `native/crates/ops-search/src/candidates_tests.rs`, `index_source_tests.rs` |
| 3. Staleness/coverage cannot masquerade as a complete answer | only `SourceState::Ready` may serve; anything else falls back to the walk; page two keeps the traversal domain (s1/s2 cursor kind) and cross-kind continuations are rejected; `truncated` stays explicit. Tests: `a_cache_directory_without_a_ready_source_falls_back_to_the_walk`, cursor-domain tests in `index_source_tests.rs` |
| 4. Resource quota, cancellation and cleanup exist | `EnumBudget` inherits the scan's remaining time; `MAX_WALK_ENTRIES`/`MAX_DEPTH` cap the walk; host cache preparation returns null on EACCES/ENOSPC and never invents a path; uninstall cleanup and lock tests live in `native/crates/ops-index/src/snapshot/{gc,lock}_tests.rs`; host tests in `test/index-cache.test.mjs` |

The verification plan for permission/file changes, invalidation, exclusions and cancellation is
listed in the issue #423 acceptance list; the negative assertions for those cases arrive with the
watcher slices. This document does not claim them as measured.

## Reproduce

```console
npm run build
cargo build --release --locked --manifest-path native/Cargo.toml
node bench/cli.mjs index-ab --self-test
node bench/cli.mjs index-ab --fresh --repeat 9 --warmup 2 \
  --worker native/target/release/dsh-ops-worker \
  --out bench/runs/index-ab/evidence.json \
  --markdown bench/runs/index-ab/evidence.md
```

- `--root <dir>` measures an operator-prepared tree instead of the generated corpus; `--fresh`
  rebuilds only the generated one.
- `--out`/`--markdown` refuse to overwrite: evidence is filed once per run/revision.
- `--dry-run` prints the resolved plan without creating anything; `--self-test` checks the recipe
  determinism, statistics and report shape with no worker and no corpus.
- The JSON carries revision, worker hash, corpus hash and every per-round sample; the Markdown is
  the table rendered above.

## Limitations

- Linux x64 only in the recorded run; the harness is platform-neutral, but no Windows/macOS number
  is claimed.
- Page cache is not dropped (no root): "cold" means first touch, and the docs say so.
- The worker is one process per call, so ~6-8 ms of process start is inside every sample; the host's
  own scheduling is excluded, and both arms share it.
- RSS is sampled, not read from `wait4`: very short calls report `n/a` instead of a guessed number.
- No index is engaged in this stack, so the numbers bound the gate's overhead, not the index's value.

## Non-goals

No MFT/USN engine claim, no daemon, no admin service, no default scan-scope change, no content
search claim (`ops_grep` keeps the walk). Nothing in this slice changes a default.
