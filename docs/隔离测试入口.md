# 隔离测试入口（#990）

## 这个入口为什么存在

一次 headless 对比只有在被测的组真正进入 OPS-PTC 路由时，才有资格谈论
OPS-PTC。在此之前，loop fixture 装配的是合成的 `fixture` 预设，字节探针
覆盖的是内置预设——一个来自 Standard 组合的绿色数字也可能被当成 OPS-PTC
证据。#980 把它定为 V1 门槛：实际走 Standard、worker 缺失或路由未知时，
这次运行判无效，并且必须把原因说出来。

## 一个组是什么

`test/lib/ptc-entry.mjs` 里的 `bootEntryGroup(root, …)` 装配一个组：

- 真实的 AgentLoop 与 Session，脚本化 provider——从不发出真实的网络模型请求；
- 按宿主 profile 的方式挂载正式单行（包入口的 `apply`），只启用目标模式，
  组跑的就是 ops-ptc 行的真实默认值；
- 组的根目录必须位于该套件独占的临时 `DSH_HOME` 内——`node test/run.mjs`
  为每套件建一个 home，入口拒绝任何位于其外的根目录。

环境摘要在装配时采集，并附在每份报告上：插件 commit（直接读 git 目录，
不起子进程）、插件版本、宿主运行时版本、平台（例如 `linux-x64`）、
worker 文件与 sha256、旁边的 staged runtime 回执以及两个摘要是否一致、
沙箱模式与工作根目录、解析后的行内开关（含批量教学默认值）、以及实际
`agentPreset` 与其模式。provider 标记为 `scripted`、
`networkModelRequests` 记为 0——模拟 provider 只能验证装配，报告必须
把这一点摆在明面上，而不是藏起来。

## 报告契约

`enterPtc(group)` 先跑最小用例：恰好一次不执行任何调用的脚本化
provider 请求，而错误的组也只配得到这一次请求。检查按固定顺序执行——
worker、preset、route、execution——第一个失败项就是报告的 reason。

- **entered**——请求的顶层恰好是 `['run_code']` 且 SDK 文本存在；只有这时
  才进入第二回合，新造一个探针文件并通过 worker 执行一段程序。证据块记录
  顶层面、preset、mode、请求计数与执行结果。
- **invalid**——报告给出 reason 与每一项检查的 findings，但不带证据块，也不带
  任何字节数或 token 数：
  - Standard 是故意的反例。它是真实组合而非桩，在 `PRESET` 一项失败，
    route 项显示 native 顶层面；
  - PTC 预设配 native executor 在 `ROUTE` 一项失败——preset 正确而传输不对，
    顶层面甚至可能一个工具都不声明；
  - 解析不到可执行 worker 的行在装配时就以 `WORKER` 失败，不会发出任何请求。

字节与成本分账刻意不在本入口采集，那是 V2 卡（#991）的范围。后续卡片
复用本入口的组与环境记录，而不是重新造一套。

## 复现

```
npm run build
npm run build:ptc
node test/run.mjs progressive-loop
```

过滤器必须命中 `progressive-loop.test.mjs`，四个入口断言与三个既有
loop 断言同处一个套件。skip 意味着 worker 没有解析出来——先跑
`npm run build:ptc`；skip 不是通过。进入这些组的只有新造的样例文件，
不读取、不报告任何真实会话、凭据或对话正文。
