# 预设与默认模式

[English](presets.md) | 中文

`ops-ptc` 是 OPS 的第五个内置增强模式。宿主只从已注册的预设声明组装会话，因此 OPS 不再用 bundle patch
插入预设行，而是在 `dsh-ops` 插件 apply 时调用宿主预设注册表，把 `ops-ptc` 运行时注册进去。本页说明注册
机制、片段与同步脚本、如何设为默认，以及禁用插件前的顺序要求。

## 运行时注册

- **入口**：`src/index.ts` 在 `apply` 开始处调用 `registerOpsPtcPreset(root)`，实现位于
  `src/presets/ops-ptc/register.ts`。
- **注册**：等宿主的 `agentPresets` 服务可用后（`ctx.inject(['agentPresets'])`），调用
  `agentPresets.register(definition)`；拥有该注入的 fiber 在销毁时调用返回的 release。同一个 root 只注册
  一次，重复 apply 不会重复注册。
- **定义来源**：随包片段 `presets/ops-ptc.patch.yml`（`package.json` 的 `files` 含 `presets`）。插件不
  自己解析 YAML：它先 `resolveAppBoot`（本包、运行中的宿主入口、profile 层依次尝试）找到宿主
  `@deepseek-ai/dsh-app-boot`，再用它的 `loadOverlayPatches('dsh-ops', FRAGMENT_FILE)` 解析，因此 `!!js`
  平台表达式保持为数据、由宿主 loader 求值；插件从解析结果里找
  `name: '@deepseek-ai/dsh-agent-preset'` 且 `config.id: 'ops-ptc'` 的声明，校验 `plugins` 非空后交给注册表。
  解析不到 app-boot 或片段读不到时同样只告警，预设不可用。
- **因此**：插件管理器里没有 `ops-ptc` 预设行；预设与 `ops_*` 工具面同属 `dsh-ops` 行，启用时一起出现，
  禁用/卸载时注册被释放、一起消失。片段缺失、畸形、宿主没有 preset registry 或注册失败都只警告一次并让
  预设不可用，不会把插件行或工具面带下来。

## 片段与同步脚本

`presets/ops-ptc.patch.yml` 是生成文件，不要手改：

- 上游：`@deepseek-ai/dsh-web-app/presets/ptc.patch.yml`；生成器
  `scripts/sync-preset-ops-ptc.mjs` 按锚点做文本替换，保留 `!!js` 表达式、注释与表达式形式，最后再解析
  自校验。
- 片段内身份：声明 id 是 `preset-ops-ptc`（片段内部标识，不是 bundle 行，也不是插件管理器行），preset 的
  `id` / `name` / `description` / `order` 为 `ops-ptc` / `OPS (PTC)` / 一句描述 / `6`；`config.plugins`
  与上游逐字节一致，压缩组仍是官方 `compaction-basic`，不引入 `dsh-compress-codex`。
- 文件头记录来源与 `sha256`，同步脚本写入新摘要。

常用命令：

```console
node scripts/sync-preset-ops-ptc.mjs              # 重新生成片段
node scripts/sync-preset-ops-ptc.mjs --check      # 校验漂移；漂移时退出码 1
node scripts/sync-preset-ops-ptc.mjs --stdout     # 只打印，不写文件
node scripts/sync-preset-ops-ptc.mjs --source <ptc.patch.yml 或其目录> [--out <file>]
```

源解析顺序是 `--source`、`DSH_WEB_APP_PRESETS`、`@deepseek-ai/dsh-web-app/presets/ptc.patch.yml` 的包解析、
向上查找 `node_modules`，最后是已安装的 `@deepseek-ai/dsh` 自带副本。解析不到源是失败而不是静默通过。
升级宿主后重新运行脚本并审阅 diff；`--check` 适合放进本地校验流程。

## 强制默认模式（`global.forceDefaultOpsPtc`）

`dsh-ops` 默认把新会话的默认预设强制为 `ops-ptc`。bundle 总开关 `global.forceDefaultOpsPtc`（中文标签
「强制默认模式为 ops_ptc」，默认 true；插件页 global 卡片可切换，YAML 也可设置）控制这一行为，在运行时
生效，而不是静态写死配置：

- **开启（默认）**：`ops-ptc` 预设注册成功后，插件通过宿主 settings 服务把 `agent-preset-registry` 的
  `selectedDefault` 写成 `ops-ptc`——与在「Agent 预设」设置页手动选择是同一机制、同一个易变字段。因此
  即使你之前手动选过别的默认，只要开关开着，下一次 apply 仍会强制为 `ops-ptc`。
- **关闭**：恢复为强制前捕获的 `selectedDefault`。若当时没有保存过值，或捕获值本身就是 `ops-ptc`（上一次
  强制的残留），则回退宿主 `config.default`，即该 profile 的官方默认模式。
- **禁用/卸载 `dsh-ops` 行**：cleanup 先恢复默认、再释放预设注册；恢复只在当前默认确实是 `ops-ptc` 时
  写入。宿主 settings 服务缺失或写入失败只记一条以 `dsh-ops: ` 开头的 warning，不阻塞卸载。
- 只有预设注册成功才会强制；片段缺失、app-boot 解析不到或注册被拒时不会强制写 `ops-ptc`，但会尽力回退残留的
  `ops-ptc` 默认（失败只告警）。
- 强制值经宿主设置层持久化到 profile 的 `cordis.patch.yml`（`agent-preset-registry` 覆盖，并写出 `default`
  字段），重启后保持；保存该行其它开关会重挂载，插件重新注册预设并按开关重新确认默认，重挂载的 teardown 与
  替代激活会先完成恢复写入再继续，避免两次写竞争。
- 该开关只改默认预设选择，不影响任何工具面、权限或预设内容。

预设在宿主选择器里的名称是 `OPS (PTC)`，描述为「代码驱动的 PTC 工具面，由 dsh-ops 的 ops_* 工具扩展。」。

## 手动设置其他默认预设

`ops-ptc` 作为默认只由上面的开关提供：开关关闭时，若默认仍指向 `ops-ptc`，插件在 apply 时会把它回退为
强制前捕获的值或官方默认（避免预设被禁用后留下悬空默认），所以不要手动把默认设成 `ops-ptc`。其他默认预设
仍照常由宿主/操作者决定：

- **宿主「Agent 预设」设置页**：选择 `standard`、`ptc` 等任一已注册预设，持久化 `selectedDefault`。
- **profile patch 显式设置**（可粘贴到 `$DSH_HOME/profiles/<profile>/cordis.patch.yml`）：

```yaml
- id: agent-preset-registry
  name: '@deepseek-ai/dsh-agent-preset-registry'
  config:
    default: standard
    selectedDefault: standard
```

`default` 是部署默认（没有用户选择时新会话使用它）；`selectedDefault` 是新会话优先解析的用户默认，宿主
设置页写入的就是它。**id 定向 patch 不深合并**：它整体替换目标行的 `config`，所以改一个键也要把另一个键
原样重述。没有 `dsh-web-app` bundle 的 profile 不加载 `agent-preset-registry` 行，这段 patch 会打印一条
非致命 `patch: entry "agent-preset-registry" not found` 并跳过，宿主设置页也不存在，默认由该 profile 自己的
组合决定。

### 风险与回退

- **开关开启（默认）时**：禁用/卸载会先恢复默认再释放注册，正常路径不会留下指向已消失预设的默认；禁用后
  重新启用插件，或在该开关关闭后用设置页选择你想要的默认即可。恢复失败只告警、不阻塞卸载，此时按下一
  条处理。
- **开关关闭时**：插件在 apply 时也会把指向 `ops-ptc` 的默认回退（捕获值或官方默认），通常无需手动切换；
  若宿主 settings 服务缺失导致恢复失败，禁用/卸载前先把默认切到其他预设最稳妥，否则新会话可能在预设
  消失后按当前定义解析失败。
- 片段缺失或宿主升级导致解析失败时，预设不可用但工具面照常工作，也不会强制默认；重新生成片段并重启宿主
  即可恢复。
- 插件管理器里找不到 `ops-ptc` 预设行是设计如此，不要尝试手动新增声明；它由插件运行时提供。
- 已存在的会话保留它们已经绑定的组合，改默认只影响之后新建的会话。

## 与官方 PTC 的差别

| 项 | 官方 PTC（`ptc`） | OPS PTC（`ops-ptc`） |
| --- | --- | --- |
| 预设声明 | `dsh-web-app` bundle 的 `presets/ptc.patch.yml` | `dsh-ops` 在 apply 时运行时注册；定义来自随包片段 `presets/ops-ptc.patch.yml` |
| 插件管理器行 | 有独立的 preset 行 | 无预设行，随 `dsh-ops` 行启停 |
| 发布面 | 官方 PTC 工具 | 与 `ptc` 分区相同：真实 PTC 呈现下的 `run_code` 加同栈类型化 SDK 文件工具 |
| 压缩 | 官方 `compaction-basic` | 同为官方 `compaction-basic`，不引入 `dsh-compress-codex` |
| 批量调用提示 | 无 | `batchingGuidance`：代码与随包 `ops-ptc` 节均默认 true，旧配置整行覆盖且缺少该节也保留默认值，显式 false 可关闭；首轮教学一次 + 按根 `run_code` 程序形状（`bypass`/`plan`/`shape`，每类每轮各锁一次、合规解锁）以 `additionalContexts` 纠偏；文案在可编辑的 `prompts/batching-guidance.md` |
| 单行配置分区 | `ptc` | `ops-ptc`（键与 `ptc` 相同，另加 `batchingGuidance`） |
| 默认预设 | 由宿主/操作者决定 | `global.forceDefaultOpsPtc`（默认 true）运行时强制为 `ops-ptc`，关闭/禁用时恢复 |
| 排序 | order 2 | order 6，排在官方行之后 |

同一套工具面开两个模式的意义就是对照臂：`ptc` 保持官方预设不变，`ops-ptc` 用同一批 API 与压缩策略，
仅多出可开关的批量调用提示。提示细节（触发条件、投递方式、编辑文案文件）见[配置参考](配置参考.md)的
OPS PTC 模式节。
